Scaling Lesson 1: Identifying Bottlenecks

Analyzing the current chat app architecture under massive message loads

The Current Flow of Messages

In our current chat app project, messaging is buffered to reduce database load. When a user sends a message, it follows this pathway:

  1. Buffering: The message is received by the application server and pushed onto a single Redis list:
    listOps.leftPush("chat_messages", messageDto);
  2. Scheduling: A scheduled Spring Batch job runs once every minute (@Scheduled(fixedRate = 60000)).
  3. Processing: The job reads the messages, queries MySQL to check if the sender and recipient exist, and maps them to entities.
  4. Writing: The processed messages are batch-inserted into MySQL via JPA saveAll().

While this design is neat for a low-traffic demo, it falls over completely when scaled to millions of messages per second. Let's see why.

Why the System Collapses

As the slider demonstrates, scaling to millions of messages per second triggers multiple critical points of failure:

  1. Redis List Lockups: Standard Redis List structures operate on a single key (chat_messages). Pushing and popping millions of times per second locks the Redis thread, causing thread starvation.
  2. Query Amplification (N+1 queries): Look at BatchConfig.java. The messageProcessor queries the database twice for every single message:
    User sender = userRepository.findById(messageDto.getSenderId()).orElseThrow(...); User recipient = userRepository.findById(messageDto.getRecipientId()).orElseThrow(...);
    At 1M msg/sec, this triggers 120 million database SELECT statements every minute. MySQL will freeze immediately.
  3. JVM Memory Out of Memory (OOM): In MessageServiceImpl.java, loading active messages calls:
    redisMessageRepository.peekMessages();
    This calls listOps.range(MESSAGE_KEY, 0, -1), loading the entire list into Java heap memory. With millions of messages, this triggers a catastrophic JVM OutOfMemoryError.
