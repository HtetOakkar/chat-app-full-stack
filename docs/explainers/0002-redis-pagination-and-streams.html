Scaling Lesson 2: Redis Pagination and Streams

Replacing O(N) range fetches with stable sharding structures

The Danger of Index-Based List Ranges

In your current code, peekMessages() loads the entire list: listOps.range(MESSAGE_KEY, 0, -1). As you correctly suggested, we could retrieve these messages **batch-by-batch** (e.g., using range boundaries like 0 to 99, then 100 to 199).

However, in highly active production applications, doing index-based pagination (using offsets) on a Redis List creates two critical problems:

  1. O(N) Traversal Time: Redis Lists are implemented as linked lists. Accessing an element at index 10,000 requires traversing 10,000 nodes. Under load, this blocks Redis's single thread, causing timeout cascades.
  2. Data Drift (Duplicates / Misses): Because your batch scheduler constantly pops items from the right, and users push new items to the left, the indices are constantly moving!

The Solution: Cursor-Based Pagination with ZSETs or Streams

Instead of using Redis Lists, high-performance chat apps use one of two structures:

1. Redis Sorted Sets (ZSET)

In a Sorted Set, every message is saved with a score representing a timestamp (or sequential ID). Instead of requesting index ranges, we query by score boundaries:

// Fetch messages older than the sentAt timestamp of the last message (cursor) listOps.zrangeByScore(KEY, "-inf", maxTimestampScore, offset, limit);

Since it uses a skip list internally, queries run in O(log(N) + M) time where M is the limit size, regardless of how deep the offset is.

2. Redis Streams

Streams are append-only logs specifically designed for real-time messaging. They support consumer groups, allowing multiple Spring Boot app instances to read batches cooperatively without duplicating work.
